title: "Webhooks"
description: "Receba notificações HTTP em tempo real quando uma transação muda de estado: pagamento aprovado, reembolso, PIX ou boleto gerado e chargeback."
---

Um webhook é uma URL sua que a Berry Pay chama sempre que algo acontece com uma
transação. Em vez de ficar consultando a API de tempos em tempos, você cadastra
um endpoint e recebe uma requisição `POST` com os dados da transação assim que o
evento ocorre.

## Como configurar

No painel da Berry Pay, abra **Integrações → Webhooks** e, na aba
**Configurações**, clique em **Novo webhook**. Preencha:

- **URL do webhook** — endpoint público que vai receber as notificações. Use
  **HTTPS**.
- **Evento** — um evento específico (veja a lista abaixo) ou **Todos os
  eventos**.
- **Produto** — restringe o webhook a um produto. O padrão, **Todos os
  produtos**, dispara para qualquer produto da conta.

Você pode cadastrar quantos webhooks quiser — por exemplo, um endpoint por
evento, ou um endpoint só para um produto. Cada webhook é disparado de forma
independente.

<Tip>
  A Berry Pay não assina o corpo do webhook. Para garantir que a chamada veio da
  Berry Pay, cadastre uma URL difícil de adivinhar — com um token secreto no
  caminho ou na query string — e rejeite qualquer requisição que não bata com
  ele.
</Tip>

## Eventos disponíveis

| Evento | Quando é enviado |
|---|---|
| `purchase_approved` | O pagamento foi aprovado / confirmado. |
| `purchase_refunded` | A compra foi reembolsada (total ou parcial). |
| `pix_generated` | O cliente gerou um PIX que ainda não foi pago. |
| `billet_printed` | O cliente gerou um boleto que ainda não foi pago. |
| `chargeback` | A transação sofreu um chargeback. |

Os eventos são derivados da mudança de status da transação no processador de
pagamento. Mudanças de status que não correspondem a nenhum evento acima não
geram webhook.

## Formato da requisição

Toda notificação é um `POST` com `Content-Type: application/json` e os headers:

<ParamField header="User-Agent" type="string">
  Sempre `BerryPay-Webhook/1.0`.
</ParamField>
<ParamField header="X-Webhook-Event" type="string">
  O evento que disparou a notificação, ex.: `purchase_approved`. É o mesmo valor
  do campo `event` no corpo.
</ParamField>
<ParamField header="X-Transaction-Id" type="string">
  O UUID da transação. Não é enviado em reenvios manuais — nesse caso, use o
  campo `transaction_id` do corpo.
</ParamField>
<ParamField header="X-Resent" type="string">
  Presente e igual a `true` apenas quando a notificação foi reenviada
  manualmente pelo painel. Em envios normais, o header não é enviado.
</ParamField>

## Como responder

Responda com qualquer status **2xx** o mais rápido possível. Qualquer resposta
fora da faixa 2xx é registrada como falha. Faça o processamento pesado de forma
assíncrona (uma fila, por exemplo) e devolva a resposta na hora.

- **Não há retry automático.** Se a entrega falhar, a Berry Pay não reenvia
  sozinha — você reenvia manualmente pelo painel, na aba **Logs**.
- **Trate duplicatas.** A mesma transação pode gerar vários eventos (ex.:
  `pix_generated` e depois `purchase_approved`), e um reenvio manual repete uma
  notificação já entregue. Use `transaction_id` + `event` para saber o que já
  foi processado.
- **Roteie pelo evento.** Use o header `X-Webhook-Event` (ou o campo `event`)
  para tratar cada tipo de notificação.
- **Responda 2xx até para eventos que você ignora** — caso contrário a entrega
  fica marcada como falha.

## Logs e reenvio

Na aba **Logs** da tela de Webhooks você vê o histórico de entregas: evento,
URL, status (**Sucesso**, **Falhou** ou **Pendente**), código HTTP da resposta e
data/hora. Abra um log para ver o payload enviado e a resposta recebida
(limitada aos primeiros 1000 caracteres). O botão de reenviar dispara a mesma
notificação de novo, com o header `X-Resent: true`.
